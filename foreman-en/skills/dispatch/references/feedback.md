# Manual testing feedback and follow-up fixes

Read this before dispatching further work when the user reports an unsatisfactory experience, missing functionality, a failure, or a change in direction for work in progress, under review, or already finished. **Decide which existing work should continue before deciding how to fix it.** Don't stop a whole batch by default or let old results advance a workflow whose goals have changed.

## 1. Classify the feedback and identify what's affected

- **Style, look and feel, interaction, or unmet functionality:** turn the feedback into a checkable requirement. Claude owns visual and interaction decisions; handle local edits in the host or dispatch them at the appropriate run level. Compare with the original brief: a missed acceptance criterion is rework; new behavior or a changed criterion is separate follow-up work, not a failure of the original brief. Don't treat changes to interfaces, permissions or data as minor adjustments.
- **Bug or crash:** identify the tested version, reproduction steps, and expected and actual behavior. Prioritize faults that could cause ongoing data damage or block the user; hold validation and integration that depend on the faulty path. Reproduce it if feasible, make the smallest fix, and check the reproduction and directly affected behavior. Use the original brief to decide whether it's rework; one bug seldom calls for replacing the whole batch.
- **Major change:** if the user replaces the goal, architecture, key interfaces or several acceptance criteria, stop spending on the old direction and preserve reusable work. Ask the user about unresolved product preferences or authorization only when they change what to do next. Relevel the work and map dependencies and packages; split and parallelize complex work as in `references/run.md`. Don't push a new goal into the old run.

Separate mixed feedback: start safe independent fixes and hold work that depends on the new direction. Record at least the tested version or worktree, the revised goal, affected behavior/files/interfaces, and dependent packages. If evidence is missing, do a targeted check first. File names alone don't tell you whether a review or test is unaffected.

## 2. Inspect actual state and choose whether to continue, redirect, stop, or redispatch

1. **Hold obsolete downstream work first.** Inspect `status --group <name>` / `status --plan <plan_id>`, then use `status --run <run_id>` for affected seats to confirm the latest round, directory and activity. Note the run IDs, plans and checks that apply only to the old goal in the task record, plus the reason, replacement batch and any work being kept. Don't launch obsolete seats or gap passes that haven't started. Keep independent work and work with still-valid dependencies running.
2. **Implementation still running:** let it finish if its goal, write scope and interfaces aren't affected. If useful work is almost done and waiting is cheaper than interrupting, let it finish and then apply the small fix. If continued writes would be wasted, conflict with the fix or pose a risk, promptly stop the affected round with `cancel --run <run_id>` rather than waiting for the three-minute health check. Keep its worktree. For a launch waiting for a local slot with no run ID yet, stop the exact background job via its original handle if supported. Check whether it acquired a slot and got a run ID in the meantime. If it cannot be stopped, hold downstream steps, report that, and stay out of files it may still write.
3. **Can the brief be changed live?** Send a small correction without restarting only if the current adapter explicitly supports addressing the live round and can confirm receipt, and the goal and write boundary stay the same. An unconfirmed message is not applied. Foreman's current headless dispatch has no such command; don't write to stdin or bypass the script by calling agents directly. If a correction can't wait, cancel as above; otherwise wait for normal completion. After confirming the old round and its writers have stopped, inspect and keep their changes. An in-scope correction can use `resume --run <latest run_id> --reason rework --level <level> --brief <delta brief>` if there is a resumable session and the same directory, plan and scope still apply. State what to check, which instruction needs correcting, and what to keep; a changed brief is not `recover`. If the session can't be resumed, the split needs changing, or the goal is new, dispatch fresh work with the current scope or have Claude take over, without bypassing configuration. Follow the rework limit and image resume options in `references/acceptance.md`.
4. **Already finished or finished during cancellation:** don't try to cancel a terminal state. Check the diff, report and version; carry forward only work that still meets the updated goal and evidence whose coverage hasn't changed. Cancellation is not a rollback. Don't clean up unowned changes or start a second writer on the same scope while the first may still be writing. For superseded packages or plans, reconcile late completion, queue or health notices as history; don't use them to launch old reviews, integrate, fill seats or auto-recover.

## 3. Continue only reviews and regression checks that still apply

- **Review running:** check the candidate, patch/attachments, context the reviewer may read, and acceptance criteria. Keep a review whose evidence still applies to the preserved code and behavior (for example, B's styling change need not stop A's isolated review). If the candidate is being replaced and the result cannot count toward delivery, promptly cancel affected seats by run ID and don't start remaining seats or a gap pass. Don't cancel finished reviews; obsolete findings are leads at most. Even if a frozen old candidate's result isn't marked `stale` by the script, it doesn't clear the new version.
- **Regression or build running:** stop only checks that can no longer verify any retained behavior or that conflict with the fix. Use `cancel --run` for a Foreman-dispatched check, or the original background job handle for a check Claude launched directly; don't kill by process name. Distinguish completed, skipped and cancelled checks. Reuse evidence only if its target, inputs and dependencies still hold; don't claim an old build or full-suite result passed on the new candidate.
- **After the fix:** run the reproduction or a targeted check first (revisit the same visual/interaction scenario; take a screenshot if needed). Then do the final verification in `references/acceptance.md` on the integrated version you'll actually deliver. Keep valid reviews and review only the changed and directly affected scope as risk warrants under `references/review.md`. If cancellation or obsolete evidence left gaps in a required review, the replacement plan covers the full scope that still lacks valid review, not just the fix. If a key interface changed, recheck dependent batches that started in parallel. Report what changed, what stopped, what evidence still applies, and what remains untested or unreviewed.
