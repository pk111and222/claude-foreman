# 人工测试反馈与补充修复

用户对正在开发、正在审查或已经完成的功能反馈体验不满、功能缺口、故障或改方向时，在继续派工前读这一篇。**先决定哪些旧工作还应继续，再决定怎么修。** 不把整组一律停掉，也不允许旧结果把流程推进到已经变更的目标上。

## 1. 主流程先分类，圈出受影响的范围

- **样式、风格、交互不满意，或功能未满足**：先把反馈变成可验收的要求。视觉和交互手感由 Claude 定稿；局部改动由 Claude 做或按执行定级交给协作方。对照原任务说明：没达到原标准是返工；新增行为或改了原标准则另起补充任务，不算原任务失败。功能涉及接口、权限或数据时不能当成小改。
- **Bug 或崩溃**：核对出现在哪个版本、复现路径、预期和实际结果；优先处理会继续造成数据损坏或阻塞用户的故障，先暂停依赖有问题路径的验证和合入。尽量先复现，再修最小范围，并验证原复现用例和直接受影响的行为。是否返工仍看原任务边界；不是每个 bug 都要重开整批。
- **大的调整**：目标、架构、核心接口或多项验收标准被替换时，停止沿旧目标继续投入，保留可复用成果；尚未定下且会改变后续做法的业务偏好或授权先找用户确认。重新定级、列依赖和工作包；复杂执行照 `references/run.md` 拆分、并行，不沿用旧任务强塞新目标。

混合反馈分开处理：能安全独立修的先做，依赖新方向的先等。最少记下用户测的版本或工作树、改动目标、受影响的功能/文件/接口和依赖它的工作包。证据不足时先做定向检查；不要仅凭改动文件名判断审查或测试不受影响。

## 2. 看实际状态，选择继续、调整、取消或另派

1. **先挡住旧范围的后续动作**：用 `status --group <组名>` / `status --plan <plan_id>` 查进度，对要处理的席位再用 `status --run <run_id>` 核对最新一轮、工作目录和活动。记下哪些 `run_id`、计划或测试只适用于旧目标（在任务记录里注明原因、替代批次及保留的成果）；尚未派出的旧席位和补漏席不再启动。独立任务及依赖仍有效的工作照常跑。
2. **执行仍在跑**：不影响其目标、写入范围或接口就让它跑完；若有效成果快完成且等它比打断更省，就先收尾，再做小修。若继续写会明显返工、和修复冲突或有风险，不等 3 分钟健康检查，立即用 `cancel --run <run_id>` 停受影响的轮次，保留工作树。已提交给后台工具、仍在等本地名额而没有 run ID 的派发，用原后台任务句柄停止（工具支持时）；也要回查它是否已抢到名额并生成了 run ID。停不下来就先挡住后续，说明情况，不碰它还可能写的文件。
3. **能否实时改指令**：只有当前适配器明确支持给指定运行轮发送消息、并能确认它收到时，才把不改目标或写入边界的小调整直接发过去；确认不了不能当成已生效。Foreman 当前的无头派发没有这样的命令，不写 stdin、不直接调用协作方绕开脚本。要立刻改方向就按上一步取消；能等就等它正常结束。确认原轮和写入进程已停、检查并保留已有改动后，原要求内的修正可用 `resume --run <最新 run_id> --reason rework --level <等级> --brief <增量说明>`，前提是会话可续接、原工作目录/计划和范围仍适用。说明里写清这次要核对的标准、纠正哪条旧指令、保留哪些改动；别把改要求写成 `recover`。没有可用会话、需要改切分或是新目标，就按当前范围新派或由 Claude 接手，不盲目绕开配置。返工次数和图像续接参数仍按 `references/acceptance.md`。
4. **已完成或取消时恰好完成**：不再尝试取消终态，先核对 diff、报告和实际版本，只有仍满足新目标、验证范围没有变化的部分可以继承。取消并不回滚；不清理来历不明的改动，不在写入是否停止不明时用同一范围派第二个写入者。对已替换的工作包或计划，迟到的完成、排队和健康通知只核对并归档，不触发旧审查、合入、补席或自动恢复。

## 3. 审查和回归只为有效版本继续

- **正在审查**：按送审候选、补丁/附件、审查会读的上下文和实际验收目标判断。审查仍针对保留的代码和行为、证据可复用时保留（例如 B 换样式，A 的隔离审查不受影响）；候选被替换、结论已不能用于交付时，立即按 run ID 取消受影响的审查席，不启动其未开始席位或补漏轮。已完成的审查不再取消；过时意见只能作为线索。即使固定在旧工作树的报告没有被脚本标 `stale`，也不能当新版本通过。
- **正在回归或构建**：只停已经不能验证任何保留行为、或者继续跑会和修复冲突的任务。Foreman 派的验证用 `cancel --run`，Claude 自己启动的后台验证用原工具的任务句柄停；不要按进程名杀一批。已完成、被跳过或取消的验证分开记；只复用测试目标、输入和依赖都不变的证据，不把旧构建/全量通过移到新版本。
- **修复之后**：先跑复现用例或定向验证（样式/交互在相同场景重看；必要时截图），再按 `references/acceptance.md` 在真正要交付的整合版本上做最终验证。保留有效审查，只重审变化及直接影响所需的范围，按风险和 `references/review.md` 定级；如果原来要求的审查因取消或过时不再完整，新计划覆盖仍缺有效审查的全部范围，不只审补丁。如果关键接口改了，也重新核对已并行接力的批次。汇报改了什么、停了什么、沿用了什么，以及什么尚未验证或审查。
